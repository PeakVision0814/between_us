### 8.7 单人态能力白名单与共享数据空间化

目标：明确并落实“单人态只是进入双人空间前的过渡状态”，避免单人态沉淀计划、随记、日历事件等业务数据，防止后续配对时出现数据归属和合并冲突。

产品规则：

- 单人态采用严格能力白名单；白名单外默认不可用
- 单人态只允许邀请对方、编辑个人资料、修改正常设置、查看必要引导和空状态
- 计划、随记、日历事件、空间状态详情等业务能力只在有效双人空间内开放
- 除个人资料和个人偏好外，业务数据必须归属于 `couple_space_id`
- 用户 ID 只能作为作者、创建者、更新者等元信息，不能替代业务数据的空间归属
- 不设计“单人业务数据配对后自动合并到双人空间”的默认路径

建议推进顺序：

1. 更新产品、架构、数据库和工作流文档，统一白名单规则与数据归属原则
2. 给首页快捷动作、计划笔记、日历写入入口增加单人态门禁
3. 确认所有共享业务写入都依赖有效双人空间，而不是仅依赖当前用户或 pending 空间
4. 复核 RLS 与前端 guard 是否一致表达“active 双人空间才可写共享业务数据”

本轮明确不做：

- 不新增单人态业务功能
- 不把计划、随记、日历事件改成个人数据
- 不做单人数据迁移或合并逻辑
- 不新增空间状态详情页
- 不扩展经期、照片、愿望清单等后期模块

### 8.8 多语言基础设施扩展

目标：把当前“简体中文 + 英文”的语言能力升级为可扩展多语言基础设施，为后续支持繁体中文、日语、韩语打基础。

状态：第一阶段已完成。

已完成内容：

- `AppLanguage` 集中式语言配置已支持 `zh-CN`、`zh-TW`、`en`、`ja`、`ko`
- `MaterialApp.supportedLocales`、设置页语言选项、持久化解析和 fallback 逻辑已从集中式语言配置派生
- 语言偏好保存为稳定 language code，并可通过 `profiles.preferred_locale` 恢复
- 旧值或未知值 fallback 到简体中文
- 登录、注册、资料补全、我们页、邀请页、空间状态页、底部导航、单人态空态和常见错误提示已完成首批多语言覆盖
- 首页、日历、计划随记等非核心深层文案允许阶段性 fallback

推进原则：

- 先升级语言架构，再补全翻译内容
- 不在一轮里同时做架构改造、全量翻译和 UI 大回归
- 新语言上线前允许阶段性 fallback，但必须在文档中标明覆盖范围
- 多语言支持不改变单人态 / 双人态能力边界

已完成推进顺序：

1. 扩展 `AppLanguage` / `Locale` / `preferred_locale` 支持 `zh-CN`、`zh-TW`、`en`、`ja`、`ko`
2. 将 `AppStrings` 从中英文二元判断改为按语言枚举分支，先保留手写字符串结构，不立即迁移 ARB
3. 扩展设置页语言选择，支持简体中文、繁體中文、English、日本語、한국어，并保证选择后持久化
4. 第一批只翻译核心路径：登录 / 注册 / 资料补全 / 我们页 / 邀请页 / 底部导航 / 单人态空态 / 错误提示
5. 第二批再补首页、日历、计划随记、设置更多页等全量文案，并做 UI 长文本回归

本阶段明确不做：

- 不一次性承诺全 App 所有文案完成日语、韩语、繁中翻译
- 不引入新的业务功能
- 不改变 `profiles.preferred_locale` 作为个人偏好的数据归属
- 不为了多语言重构页面视觉结构

完成标准：

- 用户可以在设置中选择 5 种语言选项
- 语言偏好能保存到 `profiles.preferred_locale` 并在重新登录后恢复
- 新增语言 fallback 策略明确，不出现空字符串或崩溃
- 核心路径文案完成首批翻译后，按钮、卡片、空态在移动端不溢出

### 8.9 解除双人空间机制

目标：为已经进入双人态的用户提供安全、克制、可追踪的退出机制，避免误触导致双方空间关系和共享数据状态发生不可逆变化。

状态：MVP 已完成。

已完成内容：

- 后端新增 `couple_space_exit_requests`
- 后端新增 `request_couple_space_exit()` 和 `approve_couple_space_exit(uuid)`
- active 双人空间成员可以读取自己空间的退出请求
- A 可发起退出请求；B 同意后，空间关闭，双方 memberships 变为 `left`
- 双方回到单人态白名单能力
- 共享数据不物理删除，随空间关闭通过 RLS 自然不可见
- 前端在“我们页”空间状态二级页承接退出流程
- 发起退出有两次确认；同意退出有确认弹窗；审批成功后刷新 AppController

入口建议：

- 放在双人态的 TA / 空间相关二级页中，不放在主页面第一层
- 可结合后续“空间状态”详情页承接
- 不复用单人态邀请入口的语义；单人态是“邀请加入”，双人态是“管理当前空间”

产品规则：

- 退出双人空间属于高风险操作，必须有明确警告和二次确认
- 不应默认物理删除计划、随记、日历事件等历史共享数据
- 解除后应关闭当前 `couple_space`，双方失去该空间的当前访问和写入能力
- 历史数据进入不可见 / 归档状态；永久删除必须是额外的显式危险操作
- 解除后双方回到单人态白名单能力，只保留邀请、个人资料、正常设置和必要空态

完整规划流程：

1. A 发起解除双人空间申请
2. B 同意后，空间关闭，双方同时退出双人态
3. B 拒绝后，申请取消，双方继续保持双人态
4. A 连续 3 次发起解除申请且 B 均拒绝后，系统允许强制关闭空间
5. A 发起申请后 B 24 小时内无操作，系统自动关闭空间

实现边界：

- MVP 已实现可审计的退出申请状态，而不是直接删除成员关系
- RLS 必须保证 closed 空间不再开放共享业务读写
- AppController 需要在空间关闭后刷新为单人态
- 双方都应收到清晰状态提示

MVP 明确不做：

- 不做批量删除历史数据
- 不做恢复历史空间
- 不做多空间管理
- 不做关系争议仲裁系统
- 不把解除空间和退出登录混为一谈
- 不做拒绝退出请求
- 不做发起方取消退出请求
- 不做连续 3 次拒绝后的强制关闭
- 不做 24 小时无操作自动关闭
- 不做通知推送

进入后续阶段前建议：

- 用两个真实账号手工验收邀请配对、退出请求、同意退出和双方回到单人态
- 确认语言偏好在重新登录后恢复
- 确认退出后共享业务数据不可见但未被物理删除

## 阶段 10：稳定性与私测 Beta

目标：在扩展更多模块前，先验证整体产品是否真的被情侣自然使用。

前提：手机号验证码登录（SMS OTP）必须在本阶段开始前完成。国内私测用户习惯手机号登录，仅靠邮箱验证码不够。

范围：

- 完善关键逻辑测试、共享权限测试、时间逻辑测试
- 改善离线行为、错误提示和重试机制
- 复核中英文文案质量和三种主题体验
- 小范围私测，收集真实情侣反馈
- 重点验证首页、日历、计划笔记、我们这 4 个页面的使用频率和边界清晰度

私测重点观察：

- 首页是不是足够顺手
- 日历和计划笔记会不会混
- 我们页是否真的能承接个人与双人设置
- 经期记录共享是否让用户感到安心
- 用户会不会觉得它太工具，还是刚好实用

完成标准：

- 关键场景的失败状态可见且可恢复
- 测试覆盖关键逻辑
- 私测反馈能产出明确的保留、调整、删除决策
- 团队可以基于证据决定下一批扩展模块

## 首页重构规划（已完成）

### 背景

当前首页存在信息密度过高、内容重复的问题。大卡片包含太多信息，下面的内容（下一个重要日期、快捷入口）与大卡片重复，且快捷入口没有必要放在首页（用户可通过底部导航访问）。

### 首页定位

首页是"今天和对方有关的一切"，不是"整个关系概览"。

四个主界面的职责分工：
- **首页**：今天和对方有关的一切
- **日历**：未来要发生的
- **计划笔记**：想做什么
- **我们**：两人之间的状态

### 大卡片重构方向（已完成）

**目标**：信息简洁，只展示今天最需要关注的内容。

**已实现内容**：
1. ✅ **Hero Card（情侣关系故事卡）**：超大圆角、柔和渐变、情绪文案
2. ✅ **在一起天数**：基于恋爱纪念日计算
3. ✅ **伴侣信息**：头像、昵称
4. ✅ **纪念日倒计时**：展示最近的纪念日

**暂不做**：
- 天气信息（涉及隐私和位置授权，后续再考虑）
- 伴侣心情状态（后续实现）
- 情侣场景插画（后期添加）

### 明确不做

- 不做首页等于"恋爱天数 + 纪念日 + 相册"的传统情侣 App 模式
- 不做快捷入口（用户可通过底部导航访问）
- 不做长列表、复杂筛选、大量历史数据
- 不做解释产品设计的说明文字
