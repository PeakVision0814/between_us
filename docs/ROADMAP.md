## 当前阶段：阶段 8 — 用户资料与双人身份展示

目标：把"我是谁、对方是谁、谁写了什么"展示完整。

### 8.1 个人资料完善（下一步）

目标：扩展用户资料字段，完善注册引导，为后续功能（生日提醒、经期记录）提供数据基础。

#### 数据库变更

profiles 表新增字段：
- `birthday` date（nullable）
- `gender` text not null default 'unset'，约束 check `gender in ('male', 'female', 'unset')`

#### 注册引导页改造

注册成功后进入资料设置页，收集：
- 昵称（必填）— 已有，保持
- 性别（必填）— 新增，选择"男生/女生"，决定后续功能权限（如经期记录）
- 生日（可选）— 新增，日期选择器，引导文案"方便提醒对方你的生日"

一页完成，不拆多步。必填项不填不能继续。
已有用户如果 gender 为 'unset'，下次登录时也引导补填。

#### AppController 扩展

加载并持有 gender、birthday 字段，供下游页面读取。

#### 执行拆分

第一轮：数据库 migration + 注册引导页扩展 + AppController 加载新字段
第二轮：我们页 UI 重构（见 8.2）
第三轮：个人资料编辑页（见 8.3）

#### 第一轮交付边界（锁定）

本轮只解决“资料字段落库 + 首次/补填引导 + 状态持有”这一条闭环：

- 新增 `profiles.gender` 与 `profiles.birthday`
- 把现有“仅昵称”的引导页升级为“昵称 + 性别 + 生日”
- 登录后如果 `display_name` 仍是默认占位，或 `gender = 'unset'`，都进入同一个资料设置页
- AppController 只加载并持有**当前用户自己的** `display_name`、`gender`、`birthday`

本轮明确不做：

- 不做“我们”页 UI 重构
- 不做个人资料编辑页
- 不做对方资料的 `gender` / `birthday` 展示
- 不做随记、计划、日历事件作者昵称展示
- 不在本轮处理同空间成员互看 `profiles` 的 RLS 扩展

### 8.2 我们页 UI 重构

目标：按新的信息架构重新布局"我们"页，清晰展示个人资料、对方资料、空间信息。

#### 布局方案（单列分段滚动）

```
┌─────────────────────────────────────┐
│  [我的头像]  ❤️  [TA的头像]         │
│    昵称              昵称            │
│         在一起 xxx 天               │
│  （单人模式：显示"邀请TA加入"）     │
├─────────────────────────────────────┤
│  § 我的资料                 [编辑]  │
│    昵称 · 性别 · 生日               │
├─────────────────────────────────────┤
│  § TA的资料（双人时显示）           │
│    昵称 · 性别 · 生日               │
├─────────────────────────────────────┤
│  § 我们的空间                       │
│    空间名称 · 恋爱纪念日 · 邀请码   │
├─────────────────────────────────────┤
│  § 偏好设置                         │
│    语言 · 主题 · 时区 · 通知        │
├─────────────────────────────────────┤
│  退出登录                           │
└─────────────────────────────────────┘
```

选择此方案的原因：
- 扩展性好，后续加经期共享开关、头像上传等不会破坏布局
- 信息层次清晰：我 → TA → 空间 → 设置，从个人到共享递进
- 单人模式下"TA的资料"区域自然变成邀请入口

#### 单人模式

- 顶部头像区：自己的头像 + 右侧虚线占位圆 + "邀请TA加入"按钮
- "TA的资料"区域替换为邀请卡片（生成邀请码/输入邀请码）

#### 双人模式

- 顶部显示双方头像和昵称
- "TA的资料"区域显示对方的昵称、性别、生日（只读）

### 8.3 个人资料编辑页

目标：已注册用户可以随时修改自己的资料。

- 从"我们"页"我的资料"区域的[编辑]按钮进入
- 可修改：昵称、性别、生日
- 对方资料只读，不可编辑
- 修改后同步到 Supabase profiles 表和 AppController

### 8.4 其他阶段 8 待完成项

- 单人模式首页邀请提示卡片
- 随记、计划、日历事件在双人模式下显示作者昵称
- RLS 策略：允许同一 couple space 的活跃成员互相看到 profiles

## 阶段 9：敏感数据能力与生活增强

目标：在共享能力稳定后，再逐步增加更敏感、更贴近日常生活的功能。

前提：性别字段已就位，用于判断经期记录的功能权限。

范围：

- 经期记录首版
- 仅支持手动记录，不做复杂预测
- 仅 gender='female' 的用户可以记录
- gender='male' 的用户只能查看（前提是对方明确开启共享）
- 在日历中展示经期相关信息，但和纪念日、约会保持视觉区分
- 可逐步增加计划提醒、约会提醒等增强能力

完成标准：

- 经期记录可以手动添加和查看
- 共享权限逻辑明确且可控
- 文案和交互不会让用户产生被监控感
- 敏感数据不会因为默认设置而意外暴露

## 阶段 10：稳定性与私测 Beta

目标：在扩展更多模块前，先验证整体产品是否真的被情侣自然使用。

前提：手机号验证码登录（SMS OTP）必须在本阶段开始前完成。国内私测用户习惯手机号登录，仅靠邮箱验证码不够。

范围：

- 完善关键逻辑测试、共享权限测试、时间逻辑测试
- 改善离线行为、错误提示和重试机制
- 复核中英文文案质量和三种主题体验
- 小范围私测，收集真实情侣反馈
- 重点验证首页、日历、计划笔记、我们这 4 个页面的使用频率和边界清晰度

私测重点观察：

- 首页是不是足够顺手
- 日历和计划笔记会不会混
- 我们页是否真的能承接个人与双人设置
- 经期记录共享是否让用户感到安心
- 用户会不会觉得它太工具，还是刚好实用

完成标准：

- 关键场景的失败状态可见且可恢复
- 测试覆盖关键逻辑
- 私测反馈能产出明确的保留、调整、删除决策
- 团队可以基于证据决定下一批扩展模块
