# 架构说明

这份文档定义了当前产品方向下，必须保持稳定的页面结构、内容边界和共享规则。

## 产品定位

当前产品不再以“片刻记录”为唯一核心，而是转向一款：

- 轻实用
- 低压力
- 双人共享
- 兼具情感温度与生活组织能力

的情侣 App。

一句话定义：
它是一个让两个人一起看时间、存计划、写随记、管理共同空间的生活型情侣 App。

## 视觉系统共识

已完成的风格升级是**全 App 级别的视觉系统改造**，不是单页美化，也不是功能扩张。

- 目标气质：温暖、柔和、轻盈、成熟、长期耐看
- 参考方向：情绪化陪伴感、生活感、私密空间感，而不是传统少女风、商务工具风或赛博科技风
- 亮色模式像“白天的陪伴”，暗色模式像“深夜的陪伴”；两者不是简单换色，而是同一产品的两种情绪空间
- 视觉手法以低饱和暖色、柔和渐变、大圆角卡片、克制阴影、适量毛玻璃和留白为主
- 允许参考外部产品的氛围与层次，但**不直接复制**对方的具体布局、插画、图标语义、主视觉构图和功能表达
- 当前“我们”页、首页、计划笔记和日历已经完成统一视觉 rollout；后续不应再做大范围视觉重构，应优先推进边界清晰的小功能闭环

## 主界面结构

一级导航统一为 4 个：

- `首页`
- `日历`
- `计划笔记`
- `我们`

这 4 个界面承担的是长期稳定的信息架构，不应轻易变动。

## 产品体验原则

- 首页常规但有温度，不故作复杂。
- 整个 App 应该让人觉得轻松，而不是被催着使用。
- 产品可以承载轻日记式内容，但不应该让人感觉“必须天天写”。
- 日历是时间入口，计划笔记是未定事项和随记入口，两者边界必须清晰。
- 视觉风格必须全局统一，先收敛主题、组件和信息密度，再逐页落地。
- 亮色模式与暗色模式是两种情绪空间，不只是把背景换成黑白。
- 界面要优先保证留白、呼吸感和信息层次，而不是追求塞满内容。
- 我们页承接个人资料、双人空间和设置入口，但主页面不应堆叠过多低频系统设置。
- 多语言基础设施第一阶段已完成，当前支持简体中文、繁體中文、English、日本語、한국어。
- 语言枚举、Locale、设置项和持久化已集中配置；后续新增语言应优先新增语言配置和文案资源，不应改核心页面业务逻辑。
- 核心路径已完成首批多语言覆盖；首页、日历、计划随记等非核心深层文案允许阶段性 fallback，不应在一轮里同时做全量翻译和页面重构。
- 必须支持 `system / light / dark` 三种主题模式。
- 涉及健康与隐私的数据，默认谨慎，明确授权后再共享。
- 单人态采用严格能力白名单：除邀请对方、编辑个人资料、修改正常设置、查看必要引导和空状态外，其他能力默认不可用。
- 双人态才是主要使用状态；计划、随记、日历事件和空间状态等业务能力必须建立在有效双人空间上。

## 页面边界总规则

- 有明确日期的内容，归 `日历`
- 没有明确日期的计划，归 `计划笔记 > 计划`
- 自由的日常记录与随手想法，归 `计划笔记 > 随记`
- 个人资料、双人空间入口与低频系统设置，归 `我们`
- 首页只展示状态和入口，不承担所有详情内容

## 内容归属规则

不同类型内容的协作方式不同：

- `日历事件`：双人空间业务内容，必须归属于有效双人空间，双方都可以查看与共同维护
- `计划`：双人空间业务内容，必须归属于有效双人空间，双方都可以查看和推进状态
- `随记`：双人空间业务内容，必须归属于有效双人空间，双方都能查看，但默认只允许作者编辑和删除自己的内容
- `经期记录`：属于记录者本人，只有在明确授权共享后，另一方才能查看
- `个人偏好`：只属于个人，例如语言、主题、时区
- `双人空间设置`：属于双方共享空间，例如邀请状态、空间名称、共享规则

后台数据归属规则：

- 个人资料、账号资料、语言、主题、通知预览等偏好可以归属于个人 `profile`。
- 计划、随记、日历事件、空间状态等业务数据不能以个人 `profile` 作为主归属。
- 业务数据的主归属必须是 `couple_space_id`；用户 ID 只能作为 `created_by`、`author_profile_id`、`updated_by` 等元信息。
- `pending_partner` 空间只服务邀请和关系建立，不代表业务数据已经可以写入。
- 未进入有效双人空间前，不设计“先写个人业务数据，配对后再自动合并”的默认路径。

## 四个主界面的详细信息架构草图

### 1. 首页

#### 页面目标

- 展示”今天和对方有关的一切”，不是”整个关系概览”
- 让用户一打开就知道今天最需要关注什么
- 避免做成”恋爱天数 + 纪念日 + 相册”的传统情侣 App 模式

#### 四个主界面的职责分工

- **首页**：今天和对方有关的一切
- **日历**：未来要发生的
- **计划笔记**：想做什么
- **我们**：两人之间的状态

#### 首页顶部主卡片（Hero Card）

**整体定位**：情侣关系故事卡，用于展示两个人当前的关系状态，而非数据面板。

**视觉风格**：温暖、浪漫、治愈、有陪伴感。

**卡片设计**：
- 超大圆角（24~32px）
- 宽度铺满屏幕，两侧保留安全边距（16px）
- 背景柔和渐变：
  - 亮色模式：奶油白 → 浅粉色 → 暖橙色渐变
  - 暗色模式：深紫色 → 深蓝色 → 粉紫色渐变

**内容结构**：

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  💕 我们的故事                              🌤️ (天气图标)   │
│                                                             │
│  我们已经一起走过                                            │
│                                                             │
│  128 天                                                     │
│                                                             │
│  距离周年纪念日还有 2 天                                     │
│                                                             │
│                                                             │
│                                                             │
│  ┌─────┐                                                    │
│  │  🐻  │  小熊                                             │
│  └─────┘                                                    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**内容分层**：

1. **顶部信息栏**
   - 左边：情绪价值文案（随机轮换）
     - “💕 我们的故事”
     - “🌤 今天也是想你的一天”
     - “🌙 今晚月色很温柔”
   - 右边：天气图标（后期实现）

2. **核心信息（左侧布局）**
   - 文案：”我们已经一起走过”（左侧对齐）
   - 数字：{在一起天数}（大号，占卡片约 40% 视觉权重）
   - 单位：”天”（跟在数字后面）
   - 布局：左对齐，不居中

3. **纪念日提醒（左侧布局）**
   - 内容：最近的纪念日倒计时
   - 示例：”距离周年纪念日还有 2 天”

4. **伴侣信息（左下角）**
   - 头像：伴侣头像（首字母）
   - 昵称：伴侣昵称
   - 心情：后期实现

5. **背景插画（后期）**
   - 位置：卡片右下或背景中
   - 风格：简洁、梦幻
   - 作用：增加氛围感，不抢占主体

**数据来源**：

| 元素 | 数据来源 | 说明 |
|------|---------|------|
| 情绪文案 | 随机轮换 | 预设文案列表 |
| 天气图标 | 后期实现 | 需要天气 API |
| 在一起天数 | `couple_spaces.relationship_start_date` | 已实现 |
| 纪念日提醒 | `calendar_events`（类型为纪念日） | 需要查询最近的纪念日 |
| 伴侣头像 | `partnerDisplayName` 首字母 | 已实现 |
| 伴侣昵称 | `controller.partnerDisplayName` | 已实现 |
| 伴侣心情 | 后期实现 | 需要心情状态功能 |
| 情侣场景插画 | 后期实现 | 需要设计资源 |

**当前可实现（第一阶段）**：
- 卡片整体结构和视觉风格
- 情绪价值文案（随机轮换）
- 在一起天数显示
- 伴侣头像和昵称
- 背景渐变（亮色/暗色模式）

**后期实现（第二阶段）**：
- 天气图标
- 纪念日提醒
- 伴侣心情状态
- 情侣场景插画

#### 页面不该承载的内容

- 快捷入口（用户可通过底部导航访问）
- 长列表
- 复杂筛选
- 大量历史数据
- 解释产品为什么这样设计的说明文字

#### 未来可扩展内容

- 首页卡片排序个性化
- 重要事项置顶
- 今日天气 / 节假日氛围类轻增强

### 2. 日历

#### 页面目标

- 成为所有“和日期明确绑定”的内容容器
- 让用户通过一个时间视图看清未来与纪念

#### 首屏模块顺序

1. `月视图日历`
   - 当前月份
   - 带标记的日期格
2. `选中日期详情`
   - 当日纪念日
   - 当日约会 / 提醒 / 计划后的事项
3. `近期事项列表`
   - 接下来 7 天或最近几件事
4. `新建日历项入口`
   - 纪念日
   - 约会安排
   - 提醒

#### 核心规则

- 只有已确定日期或时间的内容进入日历
- 纪念日、约会、提醒、定好的计划都属于日历
- 附着在某个日期上的备注，仍然归日历，不复制到计划笔记

#### 经期记录在日历中的位置

经期记录未来进入日历，但属于独立敏感分组：

- 不和纪念日混成同一种事件
- 默认不共享
- 只有记录者明确授权后，另一方才能查看
- 首版只做手动记录，不做复杂预测

#### 未来可扩展内容

- 周视图 / 议程视图
- 事件筛选
- 经期趋势与预测
- 与计划笔记更深联动

### 3. 计划笔记

#### 页面目标

- 承接所有还没定下日期的计划
- 承接可以随手写下来的共享随记
- 避免让用户把任何东西都塞进日历

#### 内部分区

页面内部固定拆成两个区：

1. `计划`
2. `随记`

#### `计划` 区职责

放这些内容：

- 还没有明确日期的约会想法
- 想去的地方
- 待讨论事项
- 还没决定什么时候执行的生活计划

建议模块：

- 计划列表
- 计划状态（例如：想法中 / 讨论中 / 已安排 / 已完成）
- “加入日历”动作

#### `随记` 区职责

放这些内容：

- 今天的想法
- 日常小记录
- 随手写下的文字
- 轻量共享日记

建议模块：

- 快速输入入口
- 随记时间流
- 作者标识

#### 页面核心规则

- `计划` 不是日历
- `随记` 可以像轻量日记，但不制造打卡压力
- 已经确定日期的计划应当能进入日历
- 随记不按“必须每天写”设计

#### 未来可扩展内容

- 标签
- 置顶
- 搜索
- 图片附件
- 计划转日历后的状态跟踪

### 4. 我们

#### 页面目标

- 统一承接个人资料、对方资料、空间信息和设置入口
- 强调“这是我们共同使用的空间”，而不是普通的“我的”页面
- 先回答“我是谁、我们是什么状态、这个空间是什么”，再承接低频设置

#### 当前稳定结构（主页面 + 二级页入口）

“我们”主页面已经收敛为轻量的关系空间，不再堆叠个人资料、TA 资料和设置列表：

1. `页面标题行`
   - 标题为“我们”
   - 右上角设置 icon 只在“我们”tab 显示
   - 点击进入 `SettingsMoreScreen`
2. `顶部关系 Hero`
   - 左上角展示空间名
   - 右上角个人信息 icon 进入个人资料二级页
   - 双人模式：双方头像靠近展示，中间爱心，下方显示双方昵称；当前用户昵称旁可展示性别图标
   - 单人模式：右侧为加号 / 邀请态头像，点击进入邀请二级页
   - 双人模式点击 partner 头像进入 TA 资料二级页
3. `我们的空间`
   - 作为模块入口卡，展示”空间状态”单入口
   - 不再重复展示日历、计划、随记、设置（已在 Dock 主导航中）
   - 单人模式下”空间状态”入口不可点击
   - 双人模式下”空间状态”入口可点击
   - 不在主页面重复展示邀请码、生成邀请码或输入邀请码
   - 单人模式邀请操作统一收敛到 Hero 加号 / 邀请二级页

#### 二级页承接内容

- `个人资料页`：展示并编辑当前用户昵称、性别、生日
- `TA 资料页`：双人模式展示对方信息入口，更多字段读取仍受安全边界约束；后续可承接“解除双人空间”的低频危险操作入口
- `邀请页`：单人模式承接邀请说明、邀请码生成和输入邀请码加入
- `设置与更多页`：承接语言、主题、时区、通知预览和退出登录

#### 单人模式

- 顶部关系 Hero 显示自己的身份和加号 / 邀请态头像
- 点击邀请态头像进入邀请二级页
- “我们的空间”区域不重复承接邀请操作，只保留模块入口展示
- 单人模式不是产品的主要长期使用形态，不应继续投入复杂交互闭环
- 单人模式采用严格能力白名单，只允许邀请对方、编辑个人资料、修改正常设置、查看必要引导和空状态
- 白名单之外的能力默认不可用；页面可见不等于功能可用
- 单人模式不产生计划、随记、日历事件、空间状态详情等业务数据

#### 双人模式

- 顶部关系 Hero 显示双方头像和昵称
- 点击 partner 头像进入 TA 资料二级页
- TA 的更完整资料展示仍要在安全边界确认后接入
- 后续“我们”页打磨优先服务双人模式下的空间归属感和共同信息展示
- 双人模式是主要业务使用状态，计划、随记、日历事件和共同空间信息只在有效双人空间内开放写入

#### 页面核心规则

- 个人资料和双人信息必须分段，不能混在一起
- 我们页主页面不能做成“设置堆砌页”，需要优先体现空间归属感
- 个人资料、TA / 邀请、低频系统设置都下降为二级页，不混入主阅读流
- Debug 诊断卡不应出现在产品主页面
- 涉及健康和敏感共享的配置必须有清晰解释
- 后续不应再做大范围视觉重构，优先推进明确的小功能闭环
- 视觉打磨应优先落在双人模式真实使用场景，单人模式保持清晰、轻量、可理解即可

#### 未来可扩展内容

- TA 的更完整资料展示
- 头像上传（替代首字符头像）
- 经期共享开关（放在“隐私与共享”分段）
- 共享头像 / 空间封面
- 自定义纪念日规则
- 数据导出历史

## 登录、身份与 Onboarding

### 登录基础

- 用户必须先完成登录，才能进入完整 App 界面
- 未登录状态只展示登录流程，不进入 App Shell
- 当前阶段登录方式为邮箱验证码登录（Email OTP）
- 手机号验证码登录（SMS OTP）必须在私测前完成
- 当前阶段不做微信登录
- 同一账号只允许一台设备保持有效登录；新设备登录成功后，旧设备会话失效
- 同一账号换设备后，仍应看到同一份云端数据和同一用户身份

### 验证码服务说明

邮箱验证码和短信验证码均由 Supabase Auth 内置提供，不需要自己写后端发送逻辑。

**邮箱验证码（Email OTP）：**
- 开发阶段：Supabase 自带测试邮件服务，可发送到开发者自己的邮箱
- 上线阶段：需配置正规 SMTP 服务（如 Resend、SendGrid、阿里云企业邮箱）
- 配置位置：Supabase Dashboard → Project Settings → Auth → SMTP Settings

**短信验证码（SMS OTP）：**
- 需要接入第三方短信服务商：Twilio（国际）、阿里云短信、腾讯云短信等
- 配置位置：Supabase Dashboard → Project Settings → Auth → SMS Provider
- 填入服务商的 API Key 即可，Supabase 负责发送

### 本地数据与云端数据

| 数据 | 存储位置 | 说明 |
|------|---------|------|
| 登录 session（token） | 本地 | Supabase SDK 自动缓存在设备上，App 重启后恢复登录状态 |
| profiles | 云端 | Supabase PostgreSQL，个人资料与个人偏好 |
| couple_spaces、日历、计划、随记 | 云端 | Supabase PostgreSQL，双人空间关系与共享业务数据 |
| App 偏好（语言、主题） | 云端 + 本地缓存 | profiles 表存一份，AppController 内存持有一份 |

退出登录时需清理：本地 session token + AppController 内存状态。云端数据不动。

解除双人空间不是退出登录，也不是默认删除共享数据。退出机制 MVP 已完成：A 发起退出请求，B 同意后关闭当前 `couple_space`，双方 memberships 变为 `left` 并回到单人态白名单能力；历史共享业务数据随空间关闭通过 RLS 自然不可见，永久删除必须另行确认。

退出机制当前不做拒绝、取消、连续 3 次拒绝后的强制关闭、24 小时无操作自动关闭或通知推送。这些属于后续增强，不进入当前 MVP。

### 账号与资料基础

- `auth.users.id` 是用户的真实账号标识
- `profiles.display_name` 是用户在产品内展示给伴侣和自己看的身份标识
- 登录成功后，系统先初始化 `profiles`、偏好与账号状态
- 登录成功后立即引导补全个人资料，但这一步不等于创建单人空间
- `couple_space` 不因单人业务写入而创建；如果为了邀请流程创建 `pending_partner` 空间，它也只作为配对容器，不作为计划、随记、日历事件等业务数据的写入容器
- 首次登录或后续登录时，如果 `display_name` 是默认值（"新的用户"）或 `gender = 'unset'`，进入资料设置引导
- 资料设置完成后可在后续资料编辑页中修改
- 头像暂用首字母头像（取昵称第一个字），不做图片上传

### 登录与注册分离

登录和注册是两个独立流程，不允许合并：

- **登录**：仅允许已注册用户使用，输入未注册邮箱时提示”该邮箱尚未注册”并引导去注册页
- **注册**：新用户通过注册页创建账号，同样使用邮箱验证码确认身份

Supabase 配置要求：关闭 “Enable automatic account creation on sign in”，确保 signInWithOtp 不会对不存在的邮箱自动创建账号。

分离的原因：
- 用户必须明确知道自己在做什么（登录 vs 注册）
- 防止输错邮箱意外创建空账号产生脏数据
- 注册时可引导用户了解产品定位
- 为后续手机号登录/注册预留清晰的入口结构

### 登录门禁流程

```
App 启动 → 初始化 Supabase → 检查 session
  → 有 session → 直接继续初始化用户数据
  → 无 session → 进入登录页
    → 用户输入已注册邮箱 → 发送验证码 → 输入 6 位验证码 → 验证成功
    → 用户输入未注册邮箱 → 提示”该邮箱尚未注册” → 引导跳转注册页
  → 登录/注册成功后 → 检查/创建 profile → 检查 display_name 和 gender
    → display_name 为默认值或 gender 为 'unset' → 资料设置引导页
    → 资料完整 → 直接进入主页
```

### 注册引导页（资料设置）

注册成功后（或已有用户 gender 为 'unset' 时）进入资料设置页，收集：

- **昵称**（必填）— 1-40 字符
- **性别**（必填）— 选择"男生/女生"，决定后续功能权限（如经期记录仅对女性用户开放）
- **生日**（可选）— 日期选择器

一页完成，不拆多步。必填项不填不能继续。

判断是否需要引导的条件：
- `display_name` 为默认占位值（"新的用户"）
- 或 `gender` 为 'unset'

满足任一条件即进入引导页。

第一轮范围说明：
- 本轮只完成“当前用户自己的资料补全”
- 本轮不承接“TA 的资料”展示、资料编辑页、我们页布局改造

### 注册流程

```
注册页 → 用户输入邮箱 → 调用 `signInWithOtp(shouldCreateUser: true)` → 发送验证码
  → 输入 6 位验证码 → 验证成功
  → handle_new_user() 触发器自动创建 profiles 行
  → 进入资料设置引导页 → 设置后进入主页
```

注意：`handle_new_user()` 触发器会在 `auth.users` 插入时自动创建 `profiles` 行，但触发器执行有微小延迟。前端在注册/登录成功后查询 profiles 时，如果查不到应等待重试，而非直接报错。

### 登录页要求

- 出现在 App Shell 之前
- 默认只提供邮箱验证码登录
- 首版主流程是 App 内输入 6 位验证码
- 不采用邮件链接跳转作为主流程
- 明确提示”登录后才能进入完整界面”
- 底部提供”没有账号？去注册”跳转链接
- 未注册邮箱输入后显示友好提示并引导去注册
- 保留未来增加手机号验证码登录入口的位置

### 注册页要求

- 出现在 App Shell 之前，与登录页平级
- 标题：中文”创建账号” / 英文”Create Account”
- 简短说明产品定位（情侣共享空间）
- 邮箱输入框 + 发送验证码按钮
- 验证码输入步骤
- 底部提供”已有账号？去登录”跳转链接
- UI 风格与登录页保持一致

### 资料设置引导页要求

- 全屏页面，出现在首次登录/注册后的主界面之前
- 标题从“先填写一个昵称”升级为“完善你的资料”语义
- 字段固定为：昵称（必填）+ 性别（必填）+ 生日（可选）
- 性别使用明确单选，不提供“稍后再说”或跳过
- 生日允许留空，不阻塞进入主页
- 保存按钮仅在昵称和性别都有效时可提交
- 已有用户如果 `gender = 'unset'`，下次登录后也进入该页补填
- 不允许跳过昵称或性别

## 单人模式 vs 双人模式

### 判定方式

通过 `couple_memberships` 活跃成员数判断：
- 1 人 = 单人模式（`couple_spaces.status = 'pending_partner'`）
- 2 人 = 双人模式（`couple_spaces.status = 'active'`）

### 功能分界原则

**登录是使用前提，单人态是进入双人空间前的过渡状态。** 配对不是把个人业务数据升级为共享数据，而是让共享业务能力正式可用。

单人态采用能力白名单，不采用“列出禁止项”的模式。白名单之外默认不可用。

| 功能 | 单人 | 双人 | 说明 |
|------|------|------|------|
| 邀请对方 / 进入邀请流程 | ✅ | ❌ 已配对 | 单人态核心动作 |
| 编辑个人资料 | ✅ | ✅ | 个人级数据 |
| 修改正常设置 | ✅ | ✅ | 语言、主题、通知预览等个人偏好 |
| 查看必要引导 / 空状态 / 基础页面结构 | ✅ | ✅ | 页面可见不代表业务可写 |
| 计划、随记、日历事件、空间状态详情等业务能力 | ❌ | ✅ | 必须建立在有效双人空间上 |
| 查看对方信息 | ❌ | ✅ | 仅双人态 |
| 经期记录 | ❌ | 后续阶段 | 敏感数据另行定义 |

### 设计意图

已登录但未配对用户只完成进入双人空间前的必要准备。产品不鼓励用户在单人态沉淀业务数据，也不承诺把单人业务数据自动迁移或合并到未来双人空间。这样可以避免计划、随记、日历事件在配对后的归属冲突。

## Couple Space 生命周期

共享数据模型基于一个私密的 `couple space`，其中只允许存在 2 个活跃成员。

生命周期规则：

1. 一位已登录用户创建 `couple space`
2. 该用户邀请另一位用户加入
3. 第二位用户加入后，空间成为有效双人空间
4. 达到 2 人后不允许再加入更多成员
5. 任一成员可发起解绑，但真正删除必须明确确认

`pending_partner` 状态下的空间只用于邀请生命周期和成员关系准备，不开放计划、随记、日历事件等业务写入。业务写入必须以有效双人空间为前提。

## 应用状态管理与初始化流程

### 设计原则

AppController 是整个应用的唯一状态中心。所有用户身份、空间归属、成员关系数据，统一由 AppController 持有和加载。下游页面只读取 AppController 的状态，不独立查询 Supabase。

这样做的原因：
- 避免多个页面各自初始化空间数据导致的竞态条件
- 避免重复查询造成的性能浪费和状态不一致
- 确保用户进入主界面时，所有基础数据已就绪

### 统一 Bootstrap 流程

```
App 启动
  → 初始化 Supabase SDK
  → 检查 session
    → 无 session → 登录门禁
    → 有 session → 进入数据初始化
  → 数据初始化（loadPreferences）
    → 加载 profile（display_name、gender、birthday、偏好设置）
    → 查询 couple_memberships 获取 currentSpaceId
    → 如果只有 pending_partner 空间 → 只开放单人态白名单能力
    → 如果有 active 双人空间 → 查询同空间另一成员的 display_name，并开放共享业务能力
    → 设置 appReady = true
  → appReady 后进入 App Shell
```

### AppController 持有的核心状态

| 字段 | 类型 | 含义 |
|------|------|------|
| selfProfileId | String? | 当前登录用户的 UUID |
| displayName | String? | 当前用户的昵称 |
| gender | String? | 当前用户的性别（male/female/unset） |
| birthday | DateTime? | 当前用户的生日 |
| currentSpaceId | String? | 当前用户所属的 couple_space ID |
| memberCount | int | 当前空间的活跃成员数（0/1/2） |
| partnerDisplayName | String? | 对方的昵称，仅双人时有值 |
| appReady | bool | 所有基础数据加载完毕，可安全使用功能 |

### 数据所有权规则

| 数据 | 所有者 | 下游页面如何获取 |
|------|--------|-----------------|
| 用户身份（profile） | AppController | AppScope.of(context).displayName |
| 空间 ID | AppController | AppScope.of(context).currentSpaceId |
| 成员数 / 配对状态 | AppController | AppScope.of(context).memberCount |
| 对方昵称 | AppController | AppScope.of(context).partnerDisplayName |
| 日历事件列表 | 各页面自行查询 | 仅双人态使用 AppController.currentSpaceId 作为过滤条件 |
| 计划/随记列表 | 各页面自行查询 | 仅双人态使用 AppController.currentSpaceId 作为过滤条件 |

### 禁止模式

- 禁止各页面自行创建 CoupleSpaceGuard 实例或独立查询空间归属
- 禁止各页面自行判断"用户是否就绪"，统一依赖 appReady
- 禁止在 AppController 之外持有 spaceId 的缓存副本
- 禁止写入数据时自行 ensure 空间，应直接使用 AppController.currentSpaceId

### 写入数据时的 spaceId 来源

所有需要 `couple_space_id` 的业务写入操作（创建日历事件、计划、随记、空间状态详情等），必须先确认当前用户处于有效双人空间。单人态即使存在 `pending_partner` 的 `currentSpaceId`，也不能把它当作业务数据写入容器。

邀请相关写入是例外：它属于进入双人空间前的白名单能力，可以使用 `pending_partner` 空间承接邀请生命周期。

## 敏感数据规则

经期记录属于健康相关敏感数据，必须遵循：

- 默认不共享
- 明确授权后才共享
- 只有记录者本人可以编辑
- 另一方仅在被授权时查看
- 首版不提供医疗建议式文案

## 非目标

- 把 App 做成情侣社交平台
- 把计划笔记做成复杂项目管理工具
- 在首版里就做复杂经期预测
- 在页面未稳定前扩张太多功能模块
